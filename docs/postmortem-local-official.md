# 本地官方 v1 集跑分复盘（2026-08-09，hehua v4，2 flash + 1 GLM 升级）

**终局：40/74 通关，13350/23000 分（58%）**；medium 17 + hard 20 + easy 3。
运行约 2 小时，因 GLM 配额耗尽 + 用户暂停而中止（非平台超时）。

## 里程碑：升级分流首次实战验证有效
- **GLM 解出 d-04**（Azure/云）——flash 在本地 + 托管多次都失败的题，GLM 拿下。
  证明"2 flash + 1 GLM 升级"架构本身成立：强模型确实能补 flash 的短板。
- 本轮落地的升级侧优化：flash R1 失败即升级（不等 R2 扫描）、GLM 按难度给预算
  （hard 22min）、resume 时 flash 已失败的题直升 GLM、GLM 到时限自评是否继续、
  429 长退避重连。

## 关键问题（按影响排序）

### 1. GLM 配额耗尽（本轮最大阻塞）
- 运行中段 GLM 开始持续返回 **429「资源不足」**；即使退避等待 7 次（约 5min）仍被拒，
  属**配额/额度用尽**而非短时限流。
- 配额被**烧在解不出的硬题**上：a-16（试 4 次）、f2-05（试 3 次）、e3-04（试 2 次）
  都失败——GLM 也救不回，却耗光了额度，导致后面真正需要 GLM 的题（c 系）无额度可用。
- **优化方向**：
  - 升级配额 / 换更高额度的 key（最直接）。
  - **配额感知的升级闸门**：GLM 连续 429 ≥2 次 → 熔断，暂停升级 N 分钟再试，避免空耗。
  - **升级预算倾斜**：把有限的 GLM 额度优先给"高价值且 flash 有进展（facts>0）"的题，
    而非反复给 0 进展的硬题。

### 2. c 系（exploit）9 题 + b 系（killchain）3 题全程未尝试
- 剩余 23 题里 **c-01~c-09 全部 `attempts=0`**，b-01/02/03、f2-01/04/06/08、a-05 同样 0 尝试。
- 原因不是能力，是**排序 + 时长**：EV 排序把 c/b 放最后（c 先验 0.55、预算 25min，
  b 先验 0.35、预算 50min，单位时间期望分最低），2 小时被打断时还没轮到。
- **优化方向**：
  - 给足时长（正式轮若 6h 应能覆盖到 c/b）；或
  - **为 c/b 预留时间窗**：运行到某时刻强制切入 c/b，防止被前置题耗尽时间；或
  - 适度上调 c/b 优先级（它们分值高：c 单题 300-500、b 多 flag），在"效率"与"覆盖"间再平衡。

### 3. 本地工具链缺口
- 本地（Windows）仅有 **nmap**；**sqlmap / ffuf / nuclei / gobuster / hydra 均缺失**。
- 这些烘焙在托管镜像里——正是托管 run 6661 解出 4 个 c 系的原因之一。
- 本地跑 exploit/目录爆破类题只能靠 curl + python 脚本兜底，效率与命中率都低。
- **优化方向**：本地装 nuclei/sqlmap/ffuf（至少 nuclei + ffuf），或关键轮次直接用托管镜像跑。

### 4. 硬题时间/配额止损
- a-16、f2-05、e3-04 等硬题累计消耗大量 flash 时长 + GLM 额度却无解。
- **优化方向**：给单题设**尝试次数/累计时长上限**；对"多次 0 进展（facts=0）"的题
  尽早降级跳过，把资源让给有进展或高价值题。
