## Part 1 · 标杆研究：BreachWeave 与 Cairn 架构提炼

### 1.1 BreachWeave（腾讯云黑客松智能渗透二期 冠军 1/613，最强开源）

**技术栈**：Bun + TypeScript monorepo，核心构建在第三方 `@mariozechner/pi-coding-agent` SDK 上——即"coding agent 式"的工具调用会话循环（bash/文件工具 + skill 注入），不是从零手写 ReAct。

**三角色架构（README 原文）**：
- **Manager（控制平面）**：不亲自执行利用链，只做 challenge 级调度——管理题目推进节奏、分配/回收 Solver、汇总状态、组织协作。
- **Solver（执行体）**：真正解题的 pi-agent 会话，一题可挂多个 Solver 并行探索不同方向。
- **Observer（旁路监督）**：不代替决策，持续观察最近轨迹，解决"路径偏移、状态混杂、过早结束、上下文膨胀"四大问题，做轻量纠偏。

**Manager 实现要点（challenge/manager.ts 源码实测常量）**：
- Planner 是一个独立 LLM 会话，每 **30s（DEFAULT_TICK_INTERVAL_MS）** 一轮，输入 PlannerSnapshot（markdown 表格），通过工具调用执行"启动 challenge / 启动 solver / 停止"动作；
- 硬常量：`MAX_ACTIVE_CHALLENGES = 3`（平台活跃容器上限，与我们 SDK 的 InvalidState("max active") 对应）、`DEFAULT_MAX_SOLVERS = 7`、`DEFAULT_STALE_TIMEOUT_MS = 60min`（1 小时无进展标 stale 才允许放弃）、`LIST_CHALLENGES_SYNC_COOLDOWN_MS = 10s`；
- 降噪纪律：solverHandoff ≤ **900 字符**、memory 条目 ≤220 字符、idea ≤120 字符、solver 结果 ≤180 字符；错误消息按签名节流（60s 窗口去重）；
- 调度信号全部量化进 snapshot：attemptCount、submissionCount、correctSubmissionCount、minutesSinceLastAttempt、minutesSinceLastCorrectSubmission、stale 布尔——**调度看信号不看感觉**；
- CHALLENGE_PLANNER.md prompt 反复强调"稳定优先、增量补充优先于替换、无新硬理由允许什么都不做"——防 LLM 调度抖动。

**状态分层（challenge/memory.ts）**：
- `Idea`（方向）：状态机 pending→testing→verified/failed/skipped，带 normalized 去重；
- `Memory`（事实）：kind ∈ {fact, evidence, failure, note, hint}，带 refs/source；
- 实现是文件系统（ideas/index.json + by-id/*.json + memory/entries/*.json），目录锁 + 原子写——因为多 Solver 并发读写同一题的状态；
- memory/idea 变更会**广播**给同题其他 solver（"协作同步"消息），实现轻量 stigmergy。

**Solver 工具与 prompt（kimi-security.md 实测）**：
- 工具集：`bash / read / edit / write / grep / find / ls` + `challenge_submit_flag(flag, writeup)` + `challenge_get_hint` + `security_kimi_search`（知识检索）+ 自定义 nmap 工具；
- submit_flag 返回 "correct/incorrect + N flags remaining"，**用剩余 flag 数驱动继续攻击**（多 flag 题的关键）；
- prompt 方法论精华（直接可抄）：
  - "先 curl 爬虫收集完再安全测试，爬虫时检查响应体新链接"；
  - "循环发包写 python 脚本或 shell for，不要一条条手发"；
  - "不要用 ping 判断存活（禁 ICMP），用 curl/tcp"；
  - 数值参数 IDOR：对 /router/{id} 在 ±1-1000 范围 fuzz 找 flag；
  - auth bypass 先试弱类型比较/类型转换（PHP type juggling）；
  - XSS：先 fuzz `< > " ' onclick=` 判断过滤，再构造绕过；全过滤考虑 jsfuck；
  - "判断漏洞一定不存在就不要深究"（防死磕）。

**Solver 扩展（solver/extension/ 目录）**——工程化重点：
- `large-tool-result.ts`：超大工具输出截断；
- `pentest-compaction.ts`：渗透场景上下文压缩；
- `rtk-rewrite.ts`：工具输出改写降噪；
- `scope-guard.ts`：作用域守卫（防止扫出靶机范围）；
- `challenge-observer/`：observer-loop + **ralph-loop**（周期性向会话注入提醒/续命）。

**Skills 体系（20+ 个 SKILL.md，Claude Code 风格 markdown playbook，按需注入 prompt）**：
ad-pentest、intranet-pentest、recon、targeted-pentest、nuclei-skill、ffuf-skill、pentest-fuzz-skill（下分 deserialization/idor/jwt/lfi-rfi/rce/sqli/ssrf/ssti/xss/xxe 十类 payload 库）、jwt-tool、known-product-exploit、redis-webroot-rce、remote-cmd-execution、ssrf、php-payload-builder、payloads-everything、payload-research、agent-browser（无头浏览器）、fuzz-dicts（字典库）、nps-operator。

**镜像（runtime/assets/Dockerfile，实测）**：
- 基镜 `kalilinux/kali-rolling`（多阶段构建 + USTC 镜像源）；
- apt：nmap sqlmap gobuster wfuzz dirsearch whatweb hydra john hashcat sslscan seclists redis-tools responder enum4linux proxychains4 chromium sqlite3 mysql-client binutils 7zip 等；
- pip：pwntools impacket z3-solver scapy flask-unsign pyjwt pycryptodome bs4+lxml dnspython pypsrp certipy-ad bloodhound NetExec 等；

### 1.2 Cairn（二期季军，唯一 AK 54/54；tsecbench v1 公开 67.57%）

- 哲学与 BreachWeave 相反：**通用状态空间搜索引擎**，"无角色、无工作流、无领域工具"。黑板架构（Blackboard）+ Fact/Intent/Hint 三元组图；Worker 跑 OODA 循环，仅通过共享黑板协作（stigmergy，无直接通信）；
- 三种任务类型都由同一 Worker 执行：**Bootstrap**（开局尝试直接解出）、**Reason**（读全图：目标达成？下一步探索什么？产出 Complete/新 Intent/no-op）、**Explore**（认领一个 Intent 执行，产出一条 Fact）；
- Worker 后端直接复用 **Claude Code / Codex / Pi CLI** 等现成 coding agent；Python 3.12；dispatcher 负责调度任务与容器；
- 战绩：610 队中唯一 AK（54/54），决赛第 3；赛前从未联调过，比赛当天凌晨 4 点才首次跑通全流程。

### 1.3 关键结论与复用/简化决策

**两队殊途同归的三点**：
1. 解题核心都是"coding-agent 式强工具循环"（bash + 文件 + 渗透工具），不是脆弱的手写 pipeline；
2. 都有**外置的编排层**管预算/并发/生命周期，模型只负责解题；
3. 都做**事实与方向分离的记忆** + **上下文降噪**——这是长时程任务不崩的关键。

| 模式 | BreachWeave 做法 | 我们 v1 做法 | 理由 |
|---|---|---|---|
| 编排调度 | LLM planner 每 30s 一轮 | **确定性规则调度器**（优先级队列 + 时间预算 + stale 检测） | 10 天工期；规则调度可测试、零额外 token、不抖动；LLM planner 是 v2 |
| 多 Solver 并行 | 每题最多挂多个 solver | **每题单 agent**；容器池并发 2（平台上限 3） | 8c16g 沙箱 + 弱模型，多 solver 会互相抢 CPU/token；单循环先跑通 |
| Idea/Memory 分离 | 文件锁 + JSON 存储 + 广播 | **简化为 notes 工具**：notes.jsonl（kind: idea/fact/failure）+ TODO 状态字段 | 单 agent 无并发写，不需要锁；保留"方向/事实分离"的语义 |
| Observer | 独立监督 agent + ralph-loop | **规则化看门狗**：重复命令检测、无进展检测、预算注入提醒、强制终止 | Observer 本质解决的问题用 50 行规则覆盖 80% |
| Skills playbook | 20+ 通用 skills 按需注入 | **6 维度 playbook**（markdown 文件），按 challenge 维度/level 静态选择注入 | 题目有维度标签，选择逻辑可以硬编码；内容大量借鉴其 pentest-fuzz-skill |
| 上下文压缩 | 多个 extension | **必做但最简版**：工具输出截断（head+tail 8KB）+ 超阈值滚动摘要 | 360min 长程不压缩必爆上下文 |
| host-bridge RPC | solver 容器↔宿主桥接提交 | **不需要**：SDK 与 agent 同进程（本地模式）或同在托管容器内 | 我们无此拓扑 |
| submit 驱动续攻 | 按剩余 flag 数继续 | **照抄**：SubmitResult 的 flag_count/correct_flag_count 驱动循环 | 多 flag 题核心 |
| 外置结束条件 | 系统判定而非模型自述 | **照抄**：finish 工具 + 预算强制终止 | 防模型过早宣布完成 |
| 镜像工具栈 | kali 基镜 + 全套 | **debian-slim 精选子集**（≤3GB）：nmap/sqlmap/ffuf/nuclei/hydra/gobuster + pwntools + 常用 python 库 | kali 基镜太重；v1 不打 AD/内网横向（tsecbench v1 题集无 AD 维度） |

### 2.2 LLM 客户端层（llm/）

- **不用 openai SDK，httpx 手写**（约 150 行）：网关改写下需完全控制 URL/Header/超时，手写更可控更好测；
- 请求形态：`POST {base}/chat/completions`，`tools=[...]`、`tool_choice="auto"`、`temperature≈0.3`、关闭流式（简化解析与统计）；
- **重试**：网络/5xx/429 指数退避 ×5（加抖动）；上下文超长 400 → 触发一次 compact 后重试；
- **failover**：deepseek-chat 连续失败 3 次切 qwen3-max，每题结束后尝试回切；
- **网关改写函数**（d9 沙箱实测校验精确格式，先按契约实现）：
  ```python
  GATEWAY_SUFFIX = ".tsecbench.gw"
  def rewrite_for_gateway(base_url: str) -> str:
      # https://api.deepseek.com/v1 -> http://api.deepseek.com.tsecbench.gw/v1
      u = urlparse(base_url)
      assert u.hostname in WHITELIST, "域名不在沙箱白名单"
      return urlunparse(("http", u.hostname + GATEWAY_SUFFIX, u.path, "", "", ""))
  ```
  由 `MODEL_GATEWAY=1` 触发（托管镜像 entrypoint 自动置位）；本地模式不改写；
- **统计**：每次响应取 usage.prompt_tokens/completion_tokens 按模型累计；参考榜首 242M tokens/66 分量级，设软上限（如 150M）并在报告列支。

### 2.3 工具集（core/tools.py，共 8 个）

| 工具 | 参数 | 说明 |
|---|---|---|
| `bash` | command, timeout≤300s | subprocess 隔离执行；工作目录 /tmp/work/<code>/；输出全文落盘 out/<n>.log，仅回传 head+tail（各 4KB）+ 全文路径提示，模型可用 read_file/grep 翻阅 |
| `http_request` | method,url,headers,body,follow | httpx；便于观察响应头/重定向链；SSRF 验证也用 |
| `read_file` | path,offset,limit | 读拖回的文件与自己的输出日志 |
| `write_file` | path,content | 写 exploit 脚本、payload 文件 |
| `list_dir` | path | 目录枚举辅助 |
| `grep` | pattern,path | 在大输出/源码中找线索 |
| `notes` | action,kind,content | Idea/Memory 简化体；kind ∈ idea/fact/failure/todo；每轮注入「当前认知」段 |
| `submit_flag` | flag,writeup | 走 SDK；回传 correct + 剩余 flag 数；剩余>0 注入「继续找下一个 flag」（照抄 BreachWeave） |
| `finish` | summary,give_up | 唯一合法退出；给模型体面收手出口，防硬撑 |

**防死循环四件套（规则化 Observer）**：
1. 单工具调用硬超时（bash 默认 120s，最长 300s）+ 看门狗 kill；
2. 重复检测：同一命令哈希连续 3 次 → 注入「你在重复同一命令，换思路或 finish」；
3. 无进展检测：连续 8 步无新 fact 且无正确提交 → 注入该维度「换方向清单」；
4. 预算外置：软限（预算×0.8）注入「时间不多，收尾并提交现有成果」；硬限到点强制 finish。

### 2.4 解题 Agent 主循环（core/agent.py）

```
session 组装: system.md + playbook_<dim>.md + 题面(description/难度/flag_count) + notes 快照 + 容器地址
loop (max_steps=150):
    resp = llm.chat(messages, tools)
    if finish 被调用 或 预算到点: break
    for call in resp.tool_calls:
        result = TOOLS[call.name](**call.args)     # 单结果 ≤8KB
        log event; 更新 notes / 重复检测器
        messages.append(result)
    if tokens(messages) > 0.75 * ctx: context.compact()   # 摘要中段历史
收尾: 编排层兜底补交 notes 中记录的疑似 flag
```

**System prompt 骨架（融合 BreachWeave kimi-security.md 实测有效条款）**：
1. 角色与目标：自主渗透拿 flag，格式以题面为准（常见 flag{...}）；
2. 方法论：侦察先行（curl 爬虫收集完再打点）→ 假设 → 最小代价验证 → 深入利用；循环动作必须脚本化（python 或 shell for），禁止逐条手发；
3. 纪律：不用 ping 判存活（可能禁 ICMP，改 TCP 探测）；判定漏洞不存在即换方向；新发现立即 notes(fact)，新方向记 notes(idea)；
4. 提交纪律：疑似 flag 立即 submit（重复提交幂等、错交不罚分）；剩余 flag>0 继续攻击；
5. 工具提示：大输出先落盘再 grep；nmap 先 top-ports 快扫再精扫；sqlmap 加 --batch；
6. 结束纪律：预算将尽 → finish(give_up=true)，把未竟方向写进 notes 供二次扫描接手。

### 2.5 编排与调度（orchestrate/）

**硬约束**：总预算 360min；单题最长 1h；平台活跃容器上限 3（BreachWeave 源码常量 MAX_ACTIVE_CHALLENGES=3 佐证）；hint 按比例扣分。

**时间预算方案（两轮制）**：
- 预留缓冲 45min → 净预算 315min；
- **R1 通扫**（约 250-270min）：按 level 分级限时——easy 4min、medium 8min、hard 15min、killchain 3 题各 40min；
- **R2 二次扫描**（剩余 45-65min）：只打三类题——① R1 有实质进展未出 flag（notes 有 fact）；② 多 flag 题只拿到部分的；③ R1 因预算被跳过的；限时同 R1；
- **排序**：优先级 = total_score × 维度权重 ÷ 难度系数(level)，同分取 flag_count 多的；killchain 3 题分值高但耗时，排在 easy 批之后，避免挤占快分题；
- **并发策略**：v1 采用「串行 + 预启动」——题 A 进入收尾时提前 start 题 B 容器，零切换损耗的伪并发（代码量小、不踩 max active）；d6 若有富余再升级真并发池（大小 2，留 1 名额给异常恢复）；
- **stale 判定**：单题预算内无新 fact 且无提交超过 60% 时长 → 提前 finish；
- **hint 策略**：默认不用；仅当 ① 单题已耗 ≥70% 预算且 notes 有推进中的 idea，或 ② R2 二次扫描时，才 get_hint；
- **异常处理表**：VpnCheckError → 本地模式终止并告警；ResourceUnavailable(503) → 退避重试 3 次；InvalidState(max active) → close 当前价值最低容器再继续；ChallengeNotFound → 标记跳过；任何异常不得泄漏未关闭容器（lifecycle 注册表 + finally + 启动时孤儿清扫）。

**断点续跑**：state.json 记录每题 status ∈ {pending, running, solved, partial, failed, skipped}、attempt、flags、耗时；进程重启 → 跳过 solved，重跑 pending/failed（attempt+1 换策略）；启动时对 state 中 running 的题先尝试 close_challenge 清扫孤儿容器。

### 2.6 日志与指标（metrics/，为 BSRC 作品提交服务）

- events.jsonl 全量事件，每题 transcript 另存可回放；
- report.py 产出 markdown + CSV：
  - 总览：总得分、题级/flag 级发现率、总耗时、总 tokens 与成本；
  - 按 6 维度：发现率、平均耗时、平均 token、首试成功率；
  - 单题明细表（writeup 索引）；
  - **人机对比**：人工基线（抽样子集记录人工解题耗时）vs Agent 耗时/成本；
  - 失败归因分类（侦察不足/利用失败/超时/工具缺失），佐证 v2 路线图。

### 2.7 Dockerfile 与镜像工具清单（≤3GB）

## Part 5 · 本地验证方案（三层递进）

### 5.1 离线层：无 VPN、无外网也能跑（mock 模式，d2 起每天跑）

- `mock/mock_platform.py`：本地起 Flask/httpx 可打的假平台——实现 list/start/submit/close 四个端点，内置两个真实可打的漏洞靶（一个 SQL 注入、一个命令注入，纯 python 标准库实现，Windows 直接跑）；submit 校验固定 flag；
- `mock/mock_llm.py`：脚本化假 LLM，按预录 JSON 回放 tool-calls 序列——用于**无 key、无网**验证编排全链路（调度→start→工具执行→submit→close→report）；
- `python -m agentx smoke --mode mock`：3 分钟内跑完，进 CI（也可挂 GitHub Actions 当回归）；
- 单测（pytest，全部离线）：
  - test_gateway：18 个白名单域逐一断言改写结果（含 path 保留、端口、非法域拒绝）；
  - test_tools：输出截断边界、bash 超时 kill、write/read 往返；
  - test_scheduler：63 题 × 315min 时间分配不超支、排序稳定性、stale 判定、R2 队列优先级；
  - test_state：写 state → kill → resume，容器清扫被调用（mock SDK 打桩）；
  - test_loop_guard：重复命令 3 次触发注入、预算软/硬限触发。

### 5.2 真实层：XBOW 本地模式（d3 起，经 VPN，容器在平台侧，不消耗比赛轮次）

三阶段放量：
1. **冒烟（d3）**：手挑 3 道 easy，验证端到端出旗 + close 容器无泄漏；
2. **小批（d4-d5）**：按难度分层抽 10 → 40 题，验证成功率、上下文压缩、failover；每次批跑产出 report 对比上一轮（回归防劣化）；
3. **全量夜跑（d5/d6）**：104 题全跑（预算放宽到 8h 模拟长程），重点观察：token 曲线、重复命令率、崩溃自愈（resume）、每题成本分布——这份数据同时是 BSRC 材料里「开卷 benchmark 成绩」；
- 注意 XBOW 官方 README 已声明该题集对模型已饱和（2026 年中业界约 100%），故其绝对分数只用于**回归对比与流程验证**，不代表 tsecbench v1 实战水平（实战预期按公开评测锚定：deepseek 系 60-70%）。

### 5.3 预实战层：托管镜像干跑（d8-d9）

- d8 本地 `docker run`：mock 模式全链路 + `docker images` 体积断言 ≤3GB + 工具清单脚本逐一 `--version`；
- d9 平台沙箱 dry-run：真实 360min 全流程一次，采集：网关连通性、每题实际耗时 vs 预算、沙箱 CPU/内存水位、token 总量；产出「实战参数定版」（easy/med/hard 限时、并发策略、hint 阈值）。

**验收门槛（d9 结束）**：XBOW 抽样成功率 ≥60%；单题均时 ≤6min；全程零容器泄漏；360min 无人值守不崩。满足则实战两轮策略：R1 保守参数抢基本盘，R2 用 R1 真实数据调参冲高分题。

## Part 6 · v1 / v2 边界（防止 10 天内过度工程）

**v1（8/16 交付，本方案全部内容）**：确定性调度器 + 单 agent tool-use 循环 + 6 维 playbook + notes 记忆 + 预算看门狗 + 断点续跑 + 指标报告 + Docker 镜像。

**v2 明确不做（赛后或有余力才考虑，均来自 BreachWeave/Cairn 的高阶模式）**：
1. LLM Planner 动态调度（30s 轮次 + snapshot）——先用规则版拿数据，证明规则不够再上；
2. 一题多 Solver 并行 + 不同 prompt/模型对同一题打不同方向；
3. Observer 独立监督 agent（ralph-loop 注入）——v1 用规则看门狗替代；
4. 黑板式 Fact/Intent 图（Cairn）——v1 的 notes 是其降级形态；
5. 无头浏览器工具（agent-browser/chromium）——体积换收益不划算；
6. MCP 接入、writeup 自学习库、跨题知识沉淀。

**判断原则**：任何 v2 想法在 8/16 前出现，一律记入 docs/v2.md，不动手。
