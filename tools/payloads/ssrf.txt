Server-Side Request Forgery (SSRF) is a vulnerability where an attacker forces a server-side application to make requests to an unintended destination. In a typical SSRF scenario, the application accepts a URL (or other forms of input that construct a URL) from a user and attempts to fetch the resource.
If the application does not properly validate or filter the input, an attacker might manipulate the request to target internal resources that are not directly accessible from the outside, such as:
*   **Internal APIs and Services:** Accessing administrative interfaces, databases, or internal tools that trust traffic originating from within the network.
*   **Cloud Metadata Services:** Cloud environments (like AWS, GCP, and Azure) provide metadata services accessible via specific IP addresses (e.g., `169.254.169.254`). If an SSRF vulnerability can reach this endpoint, it might expose sensitive information like temporary credentials or configuration data.
*   **Internal Network Scanning:** Using the vulnerable server to map the internal network, identifying open ports and available services.
When developers attempt to block SSRF by creating blocklists (e.g., blocking requests to `127.0.0.1` or `localhost`), attackers often look for ways to bypass these filters. This relies on how different components parse URLs or resolve hostnames. Common techniques involve:
*   **Alternative IP Representations:** Using decimal, octal, or hexadecimal representations of an IP address (e.g., `0x7f000001` for `127.0.0.1`) to bypass simple string-matching filters.
*   **DNS Rebinding:** A technique where an attacker controls a DNS record for a domain they own. Initially, the domain resolves to a public, safe IP address (passing initial checks). However, on a subsequent lookup (when the server actually makes the request), the DNS record is changed to resolve to an internal IP address.
*   **URL Parsing Discrepancies:** Exploiting differences in how various libraries and components parse URLs. What a security filter interprets as the hostname might differ from what the underlying HTTP client uses to make the connection.
Defending against SSRF requires a layered approach, focusing on strict validation and the principle of least privilege.
1.  **Strict Input Validation (Allowlisting):**
*   The most effective defense is to avoid making server-side requests based on user input whenever possible.
*   If user input is necessary, use an allowlist of permitted domains, IP addresses, and protocols (e.g., only allowing `http` and `https`).
*   Validate that the input matches the expected format exactly.
2.  **Network Segmentation and Firewall Rules:**
*   Isolate critical internal services. The application server should not have unrestricted network access to all internal resources.
*   Implement firewall rules (e.g., using iptables, cloud security groups) that explicitly block outbound traffic from the application server to internal networks and metadata endpoints (like `169.254.169.254`), unless explicitly required.
3.  **Disable Unused URL Schemes:**
*   Restrict the protocols that the application is allowed to use. Disable schemes like `file://`, `gopher://`, `ftp://`, or `dict://` if only HTTP/HTTPS is expected.
4.  **Do Not Rely Solely on Blocklists:**
*   Blocklists are often incomplete due to the many ways an IP address or URL can be represented. While they can provide some defense-in-depth, they should not be the primary control.
5.  **Authenticate Internal Requests:**
*   Require authentication for internal services, even if they are only accessible from within the network. This ensures that even if an SSRF occurs, the attacker cannot interact with the service without valid credentials.
